### 1. Определение типа приложения

Согласно классификации главы 14 «Выбор типа приложения», наше приложение относится к типу **«Веб-приложение»**.

**Обоснование:** Приложение ориентировано на массового пользователя, доступ к нему должен осуществляться через браузер с любого устройства. Веб-приложения идеально подходят для этого сценария, обеспечивая простоту развертывания и независимость от клиентской платформы.

### 2. Выбор стратегии развёртывания

Основываясь на главе 13 «Физические уровни и развертывание», выбираем стратегию **распределенного (n-уровневого) развертывания**.

**Обоснование:**
1. **Безопасность:** Согласно шаблону безопасности, мы можем использовать модель «доверенная подсистема» и разместить базу данных за дополнительным межсетевым экраном, изолировав её от прямого доступа из интернета.
2. **Масштабируемость:** Распределенная архитектура позволяет горизонтально масштабировать каждый уровень независимо по мере роста нагрузки.
3. **Управляемость:** Централизация бизнес-логики и данных упрощает их обслуживание и обновление.

### 3. Обоснование выбора технологии

**Слой представления (Client)** - HTML5, CSS3, JavaScript (Стандарт для веб-приложений, обеспечивающий максимальную кросс-платформенность)
**Слой представления (Server)** - ASP.NET Core MVC (Четкое разделение логики (Model-View-Controller), улучшает тестируемость)
**Бизнес-слой** - C# (.NET Core) (Зрелый, производительный язык; выделение компонентов бизнес-логики)
**Слой доступа к данным** - Entity Framework Core (ORM ускоряет разработку, соответствует шаблону Repository) **База данных** - PostgreSQL (Надежная, ACID-совместимая СУБД с открытым кодом)
**Веб-сервер** -  Nginx (Высокопроизводительный reverse proxy для балансировки нагрузки)

### 4. Показатели качества (Quality Attributes)

В соответствии с главой 16 «Показатели качества»:

1. **Безопасность:**
   - Аутентификация и авторизация пользователей
   - Хеширование паролей (bcrypt)
   - Использование HTTPS для всех соединений

2. **Производительность:**
   - Время загрузки страницы < 2 секунд
   - Время ответа API < 200 мс

3. **Масштабируемость:**
   - Горизонтальное масштабирование веб-серверов и серверов приложений
   - Компоненты без сохранения состояния

4. **Удобство обслуживания:**
   - Четкое разделение на слои
   - Следование принципам SOLID
   - Наличие Unit-тестов

5. **Надежность:**
   - Обработка ошибок и исключений
   - Централизованное логирование

### 5. Сквозная функциональность (Cross-cutting Concerns)

**Аутентификация и Авторизация** - JWT-токены в заголовке Authorization; отдельный middleware-компонент
**Обработка исключений** - Централизованный middleware; паттерн Exception Shielding
**Логирование** - Структурированное логирование (JSON) с использованием Serilog
**Валидация данных** - Data Annotations в DTO
**Кэширование** - Распределенный кэш Redis с TTL |

### Выявленные проблемы и недоработки

- **Неполное внедрение DI** — зависимости создаются вручную
- **Репозиторий не для всех сущностей** — только UserRepository
- **DTO используются не везде** — данные передаются напрямую
- **Middleware работает нестабильно** — неполная обработка ошибок
- **Отсутствие модульных тестов** — низкая уверенность в корректности
- **Нет интерфейсов для сервисов** — сложность тестирования

## Часть 3. Сравнение и рефакторинг

### 1. Сравнение архитектур «As Is» и «To Be»

 **Разделение на слои** 
 «As Is» Отсутствует. Код UI и бизнес-логика смешаны 
 «To Be» Четкое разделение на слои Presentation, Business, Data 
**Инкапсуляция** 
 «As Is» Cлабая. Шаблон знает о внутренних данных, но плохо работает 
 «To Be» Слои скрывают детали реализации за интерфейсами 
**Связность**
 «As Is» Средняя. Функции разных областей немного смешаны 
 «To Be» Высокая. Каждый компонент отвечает за свою задачу 
**Тестируемость** 
 «As Is» Низкая. Невозможно тестировать изолированно 
 «To Be» Высокая. Unit-тесты для каждого слоя 
**Повторное использование** 
 «As Is» Средняя. Логика иногда дублируется 
 «To Be» Высокое. Сервисы переиспользуются 

### 2. Отличия и их причины

**Отличие 1: Отсутствие многослойной архитектуры**
- *Причина:* MVP, созданный для быстрого запуска. Основное внимание функциональности.

**Отличие 2: Смешение логики представления и бизнес-логики**
- *Причина:* Использование шаблонизатора с возможностью встраивания логики.

**Отличие 3: Тесная связь с фреймворком**
- *Причина:* Отсутствие абстракции объектов session и user.

**Отличие 4: Отсутствие слоя абстракции для доступа к данным**
- *Причина:* Прямые SQL-запросы в контроллерах на ранних этапах разработки.

### 3. Пути улучшения архитектуры (рефакторинг)

**План рефакторинга для достижения архитектуры «To Be»:**

1. **Внедрение шаблона Separated Presentation**
   - Подготовка данных в контроллере
   - Передача в представление через ViewModel
   - Переход к паттерну 

2. **Выделение бизнес-слоя (Service Layer)**
   - Создание сервисов: AuthenticationService, ProfileService
   - Вынос бизнес-логики из контроллеров

3. **Внедрение шаблона Repository**
   - Создание репозиториев через интерфейсы (IUserRepository)
   - Абстрагирование доступа к данным

4. **Применение Dependency Injection**
   - Внедрение зависимостей через конструкторы
   - Повышение тестируемости и гибкости

5. **Создание DTO (Data Transfer Objects)**
   - Изоляция слоя представления от моделей данных
   - Использование UserProfileViewModel

## Вывод

В ходе лабораторной работы был проведен анализ архитектуры веб-приложения «MatchUp». 

Текущая архитектура (As Is) представляет собой простое монолитное приложение, где все компоненты сильно связаны, что характерно для начальной стадии разработки.

Целевая архитектура (To Be) спроектирована в соответствии с лучшими практиками, изложенными в «Руководстве Microsoft по моделированию приложений». Она представляет собой многослойное приложение с четким разделением ответственности, слабой связанностью и централизованным управлением сквозной функциональностью.

Сравнительный анализ выявил ряд критических отличий. Для их устранения будет произведен поэтапный рефакторинг, направленный на внедрение ключевых архитектурных шаблонов: MVC, Service Layer, Repository и Dependency Injection. 

Реализация этих улучшений позволит повысить тестируемость, масштабируемость и удобство обслуживания приложения, что обеспечит его успешное развитие в будущем.
