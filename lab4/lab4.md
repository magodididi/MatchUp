# Лабораторная работа №4  
**Тема: «Парное программирование»**

**Проект:** MatchUp — веб-приложение знакомств
Функционал планируемый к реализации: свайп-анкеты, система лайков/матчей, чаты.

## Задача, которую мы реализовывали

В паре мы полностью разработали основной функционал знакомств:

- маршрут `/swipe` — показ случайной подходящей анкеты + расчёт match_score по общим хобби и полю `looking_for`
- обработка действий like / pass (`/swipe/action`)
- автоматическое создание взаимного матча при обоюдных лайках
- страница «Мои матчи» (`/matches`) с отображением общих интересов
- базовая структура чатов (хранение сообщений)

Также провели миграцию данных: добавили поле `gender` в `storage.py`.

## Использованные стили парного программирования

Мы попробовали два основных стиля, рекомендованных в задании:

1. **Ведущий — ведомый** (и переход в **На равных**)  
   Один объяснял устройство работы (`load_users` / `save_users`), миграции данных, работу сессий Flask. Второй реализовывал. Позже роли выровнялись — работали примерно на равных.

2. **Пинг-понг**  
   Один пишет «тест» или ожидаемое поведение (например: «при like должно добавиться в likes и создаться матч при взаимности»), второй реализует. Потом меняемся.

**Самым эффективным оказался стиль «Пинг-понг»**.

### Почему пинг-понг оказался лучше?

- чёткое разделение ответственности 
- меньше путаницы  
- оба постоянно вовлечены
- сразу видны ошибки в логике (ещё до написания кода)  
- идеально подходит для Flask, где много маленьких логических блоков

## Результаты и впечатления

### Что получилось (положительные моменты)

- Код вышел чище и надёжнее — поймали несколько багов ещё на этапе «теста» (например, mutable default в словарях чатов)  
- Обмен знаниями: один узнал про `request.form.getlist("hobbies")` и расчёт увлечений; второй про миграцию данных и анимации CSS в шаблонах и особенности UX/UI - design 
- Коллективное владение кодом — теперь любой из нас может спокойно править свайп, матчи или чаты  
- Дисциплина — стыдно лезть в телефон, когда второй смотрит
- Скорость разработки почти не упала, а качество кода заметно выросло (меньше ошибок ≈ 50–60%, как в исследованиях)

### Что не получилось 

- Один отвлекался на телефон - договорились о 25 минутных спринтах
- Споры по стилю кодирования (разделение логики и файлы) - уступки согласно логике
- При одновременном сохранении возникали конфликты и порча файла. Научились сохранять изменения строго по очереди после обсуждения - проблема исчезла
- Не сразу договорились о едином стиле обработки ошибок: один использовал `flash()`, второй — просто редирект без сообщений пользователю. Приняли правило: все пользовательские ошибки показываем через `flash()` так интерфейс стал дружелюбнее.
- Отладка шаблонов Jinja2 занимала много времени — ошибки в `{% if %}` и фильтрах не сразу видны. Перешли на Live Share + запуск сервера в debug-режиме у обоих так находить и исправлять стало в разы быстрее.
- После лайка матч иногда создавался только у одного пользователя (забыли синхронизировать обе стороны) - Добавили явную двустороннюю синхронизацию в функции создания матча → теперь всё работает корректно.
