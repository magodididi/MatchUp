## Лабораторная работа №5: “Технический долг. Устранение долга”

Технический долг (technical debt) — это метафора, описывающая последствия принятия быстрых, но неоптимальных решений в разработке ПО, которые в будущем приводят к дополнительным затратам на поддержку и развитие. Согласно материалам (статьи Хенрика Книберга и ATDD-подход), технический долг может быть "хорошим" (осознанным, для ускорения релиза) или "плохим" (из-за халатности). Для его устранения рекомендуется использовать ATDD (Acceptance Test-Driven Development), Definition of Done (DoD) и регулярный рефакторинг.

ATDD (Acceptance Test-Driven Development) — подход, где тесты на основе пользовательских сценариев пишутся до кода. Это помогает:

- Уточнить требования.
- Обеспечить покрытие функциональности.
- Обнаружить долг на ранних этапах.
- Автоматизировать регрессионное тестирование.

ATDD from the Trenches — практические примеры применения ATDD.

В проекте MatchUp (Flask-приложение для dating-сервиса) мы проинспектировали код на признаки технического долга, разработали план устранения, оценили его, сравнили с недоимплементированными фичами, сделали выводы и предложили коррективы в план разработки.

# 1. Инспекция проекта на наличие технического долга

**Непонятный / нечитабельный код:**
В routes.py код в целом читаем, но есть длинные функции (например, @auth.route("/profile", methods=["GET", "POST"]) — ~100 строк с обработкой форм, файлов и расчетов). 
Нет docstrings в большинстве функций (кроме calculate_zodiac). 
В HTML-шаблонах (например, profile.html) — огромные inline-стили (~8000+ символов), что затрудняет чтение и поддержку.
**Долг:** Средний. Код функционален, но требует рефакторинга для читаемости.

**Дублирующийся код:**
Загрузка/сохранение пользователей (load_users/save_users) повторяется в каждой route (например, в register, login, profile, swipe_action и т.д.). Нет централизованного сервиса.
В чате: добавление сообщений дублируется для sender и receiver (me["chats"][partner].append(message) и partner_user["chats"][me_login].append(message)).
**Долг:** Средний. Немного копипасты, риск ошибок при изменениях.

**Отсутствие автоматизации (тестов, сборки, развёртывания):**
Есть unit-тесты (test_auth.py, test_utils.py и др.), но покрытие неполное (нет интеграционных тестов для чатов/свайпа, нет тестов на UI/шаблоны).
Сборка/развертывание: Нет Dockerfile, CI/CD (GitHub Actions/Jenkins). Запуск вручную via Flask.
**Долг:** Критический. Проект не тестируется автоматически, что приводит к регрессиям.

**Запутанная архитектура и ненужные сложные зависимости:**
Архитектура: Blueprint "auth" содержит все (auth, profile, swipe, matches, chat) — monolithic. 
Ненужные: В routes.py импорты (uuid, os) используются минимально; calculate_zodiac — простая функция, но hardcoded даты.
**Долг:** Средний.

**Медленные / неэффективные средства:**
Нет caching (например, для кандидатов в swipe).
**Долг:** Высокий для production, но для dev — приемлемо.

**Незакоммиченный код / долгоживущие ветки:**
Код закомичен и есть локально как файлы, в main. Git — есть версионирования.
**Долг:** Отсутствует.

**Отсутствие / несоответствие технической документации:**
Есть README, API docs (Swagger). Комментарии присутствую.
HTML: Есть описание шаблонов.
**Долг:** Отсутсвует. Новый разработчик справится.

**Отсутствие тестовой среды:**
Нет staging/dev/prod. Всё на localhost, с hardcoded путями (UPLOAD_FOLDER).
**Долг:** Высокий. Риски в production.

**Длинные циклы интеграции / отсутствие непрерывной интеграции:**
Нет CI (Travis/Jenkins). Интеграция — manual merge.
**Долг:** Высокий. Нет автоматизированных builds/tests.

**Общий объём долга:** Высокий (7/9 признаков присутствуют). Проект работает, но есть правки для устойчивости.

# 2. План мероприятий по устранению долга

План основан на ATDD: Добавим тесты перед рефакторингом. Используем DoD: "Код чистый, тесты проходят, deployed".

**Мероприятие 1: Рефакторинг читаемости и дублирования (признаки 1,2).**
- Вынести load/save_users в UserService class.
- Разбить длинные routes на sub-functions (e.g., handle_profile_update).
- Извлечь общие стили из HTML в static/style.css.
- Добавить docstrings ко всем функциям.

**Мероприятие 2: Введение автоматизации (признак 3).**
- Добавить pytest: Тесты для validators, security, routes (mock Flask).
- Настроить GitHub Actions для CI (build, test on push).

**Мероприятие 3: Улучшение архитектуры (признаки 4,5).**
- Добавить caching (Flask-Caching) для swipe candidates.

**Мероприятие 4: Документация и окружения (признаки 6,7,8).**
- Создать README.md с setup, API endpoints.
- Добавить Docker для dev/staging/prod.
- Настроить .env для конфигов (secret_key, DB_URL).

**Мероприятие 5: CI и интеграция (признак 9).**
- Интегрировать CI/CD с deployment на Heroku/Vercel.

**Порядок:** 1→2→3→4→5 (тесты сначала).

# 3. Оценка плана мероприятий

Оценка в часах (assuming 1 dev, средний опыт):

- Мероприятие 1: 0,5 часа (рефакторинг кода + стилей).
- Мероприятие 2: 6 часов (написание тестов + CI setup).
- Мероприятие 3: 2,5 часов (caching).
- Мероприятие 4: 6 часов (docs + Docker).
- Мероприятие 5: 4 часа (CI/CD integration).

**Итого:** 16 часов (~2 дня full-time).

# 4. Сравнение объёма долга и недоимплементированных фич

**Недоимплементированные фичи (на основе кода):**

- Реальная отправка email в forgot_password (сейчас print токена) — ~4 часа (Flask-Mail + SMTP).
- Уведомления в чате (real-time via WebSocket/Flask-SocketIO) — ~8 часов.
- Безопасность: Нет rate-limiting, CAPTCHA — ~5 часов.
- Масштабируемость: Пагинация в matches/chats — ~4 часа.

**Итого недоимплементированных:** ~21 час.

**Сравнение:** Долг (16 ч) < Недоимплементированные (21 ч). Но долг влияет на будущие фичи (e.g., без тестов новые фичи рискованны).

# 5. Выводы и обоснование необходимости устранения долга

**Необходимость:** Частичная. Полное устранение не срочно (проект dev-stage), но игнор приведёт к "плохому" долгу (рост как на графике "Как бывает"). 

**Обоснование:** Без тестов проект не production-ready; дублирование замедлит добавление фич (e.g., real-time chat).

**Коррективы в план разработки:**

- Приоритизировать: Сначала тесты + рефакторинг (16 ч), затем фичи (email, notifications — 12 ч), потом остальной долг.
- Ввести DoD: Каждая фича — с тестами, docs.
- Итерации: Каждые 2 недели — рефакторинг 20% времени (как в ATDD).
- Обновлённый план: Неделя 1 — Устранение ключевого долга. Неделя 2 — Фичи. 

**Итог:** 

В проекте был накоплен опреденный технический долг (дублирование, монолит, неэффективное хранение), но были и сильные стороны (тесты, безопасность паролей). Устранение через ATDD позволило снизить долг, сделать код поддерживаемым. Общий план был: 20% времени на рефакторинг в каждой итерации. Результат: Переход от "Как бывает" к "Как мы хотим" - выполнено на 100%.
